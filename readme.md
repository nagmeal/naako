# なあこ

小さいローカル LLM（gemma4:e4b 級）でもタスクを回せるように工夫した、個人開発の AI エージェントです。

設計目標は「高性能なモデルで解決しない」こと。小さいモデルの弱さ（長い文脈が苦手、書式が崩れる、やっていないことを「やった」と報告する、など）を、モデルではなく仕組みの側で補います。

## 仕組み

全体は単一エージェントで、計画 → 実行 → 報告の流れ（最大10ステップ）です。その上で、次の仕組みが段階の間をつないでいます。

- **結果台帳（`.workspace/results.json`）**
  段階どうしの受け渡しは、モデルの文章ではなく検証可能な結果（スクリプトの生出力・終了コード・成否）で行います。要約や報告は台帳の「出力」を根拠にし、モデルの解釈は「補足」として区別します。

- **要点だけを保持する作業記憶（`.workspace/points.json`）**
  各タスクの結果は、圧縮専用の呼び出しで要点1つ（100字以内）に落とし、次の段階へは要点のリストだけを渡します。詳細は台帳に置いたままにします。要点が上限（10件）を超えたら、最初の目標に照らして「今一番大事なもの」だけを残します。

- **下書きの蓄積（`.workspace/draft.md`）**
  成果物は最後に一気に生成するのではなく、各段階が少しずつ書き足した蓄積として作ります。最終報告は、報告役の短い導入と、下書きそのものの提出で構成されます。これにより、成果物の大きさが1回の生成量に縛られなくなります。

- **書き足し前の検証**
  文章タスクの出力は、下書きと要点に反映する前に検証します。「この実行役は文章を作ることしかできない」という前提に反する行為の主張（していない検索を「した」等）は作り話として除きます。除いた行も台帳には全文が残ります。スクリプト系の出力はハーネスが作る事実なので検証しません。

- **最終チェック**
  報告の前に「最初の目標を達成したか」を要点と台帳の成否で照合します。未達と判断したら、詳細を見返して1周だけ再計画します。

## スキル

能力は Agent Skills 形式（フォルダ＋`SKILL.md`）のスキルとして外付けします。現在5つあります。

| スキル | 内容 |
|---|---|
| plan-lint | 計画テキストの書式・粒度を決定的にチェックする（スクリプト） |
| web-search | DuckDuckGo Lite で検索し、上位5件のタイトル・URL・概要を返す（スクリプト） |
| code-agent | Claude Code にコード作業を委譲する（スキル拡張専用。APIモードでは封印） |
| wiki-ingest | `docs-inbox/` の資料（xlsx / pptx / txt / md / csv）を wiki に取り込む |
| wiki-search | wiki のページをキーワード＋文字 bigram で決定的に検索する（スクリプト） |

## wiki

`docs-inbox/` に資料ファイルを置いて取り込みを依頼すると、内容を抽出して `wiki/pages/` に Markdown ページ化し、`wiki/index.md` の目次を再生成します。読めないファイル（対象外の形式・破損など）は無理に読まず、inbox に残して報告します。その後は wiki-search で引いて答えられます。

## 前提条件

- Python 3
- [Ollama](https://ollama.com/) がインストールされ、起動していること
- モデル `gemma4:e4b`

```bash
ollama pull gemma4:e4b
pip install requests
```

code-agent スキルを使う場合のみ、Claude Code と Ollama 経由のクラウドモデル（gemma4:cloud）を使います。なあこ本体（計画・実行・報告・要約）はローカルモデルで統一しています。

## 実行方法

```bash
# 1回だけ依頼する
python main.py "Gemma 4の最新情報を調べて"

# 引数なしで対話モード
python main.py
```

## APIモード

ジョブ形式の HTTP API と、依存なしの簡易 UI が使えます。

```bash
python api_server.py
# ブラウザで http://127.0.0.1:8765/ を開く
```

- `POST /run` {request} → ジョブ投入、`GET /jobs/{id}` で状態・報告・台帳を取得
- APIモードではモデルをローカルに固定し、code-agent は封印されます（仕事のテキストを社外クラウドに出さないための線引きです）
- 環境変数: `NAAKO_API_TOKEN`（認証トークン）、`NAAKO_API_PORT`（既定 8765）、`NAAKO_API_MODEL`（既定 gemma4:e4b）
- 回帰確認用スモークテスト: `python scripts/api_smoke.py`

## ファイル構成

| ファイル | 役割 |
|---|---|
| `main.py` | エントリポイント（計画の解釈、実行ループ、最終チェック） |
| `agents.py` | 計画・実行・圧縮・検証・報告を行うエージェント本体 |
| `llm_client.py` | Ollama `/api/chat` の呼び出し（思考モード無効化などの調整を含む） |
| `settings.py` | モデルやエージェント設定（報告役だけ性格付けを分離） |
| `skills.py` | スキルの読み込み（`input:` / `timeout:` / 除外リスト対応） |
| `workspace_manager.py` | `.workspace/` の状態管理と、実行ごとのローテーション |
| `wiki_ingest.py` | 資料の抽出と wiki ページ化（標準ライブラリのみ） |
| `api_server.py` / `ui.html` | APIサーバーと簡易 UI（標準ライブラリのみ） |

実行状態は `.workspace/` に置かれ、実行ごとに `archive/` へ退避されます（`plan.txt` / `results.json` / `points.json` / `draft.md` / `memo.txt`）。

## 設計原則

- 1タスク＝動詞1つ・成果物1つに細かく割る
- 決められることは、モデルに任せずスクリプトで決定的に決める
- エージェントの自己報告は鵜呑みにせず、成果物（ファイルの実在・差分・出力）を検証してから取り込む
- 小さいローカルモデルを前提にし、工夫で補う。クラウドモデルは Claude Code 経由だけに限る

## 現状

個人プロジェクトとして開発中です。小さいモデル前提のため、計画や要点の質には実行ごとにばらつきがあります。それでも「資料を入れる → wiki が育つ → 引いて答える」「調べて、要点を残して、成果物を書き足す」といった一連の流れが、ローカルモデルだけで回るところまで来ています。
